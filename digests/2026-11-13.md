## 重点话题

### 1. Gemini 4 Hydrogen 和 Orchestrator：多模型协作从“静态路由”变成“轨迹内交接”

**发生了什么**
- Google 于 2026-11-12 发布 Gemini 4 Hydrogen，定位是日常编码和 Agent 工作流的快速执行模型，与前沿模型 Carbon、Argon 搭配。官方数据：Artificial Analysis Intelligence Index 默认 high 档 51 分（Argon 50 分），最高 xhigh 档 54 分；Terminal-Bench 4.1 为 57%（Gemini 3.8 Flash 为 18.2%），任务完成速度约为 3.8 Flash 的 2.5 倍，捏造性陈述减少 5 倍以上；1M 上下文全段统一定价，每百万输入 $1.50、输出 $7.50；新增 xhigh 共四个思考档位。（[Google Blog, 2026-11-12](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-hydrogen/)）
- Agent 相关的官方指标：Agent Arena 第 5，Vals Tax Agent Bench 第 1（52.3%），Agents' Last Exam v1.1 为 71.6%；会原生并行批量发起读文件和搜索调用，合作方测得比 3.8 Flash 快 2 到 2.8 倍、token 少 12% 到 23%。安全方面称 Agent 任务中越权行为最多减少 81%，在 Gray Swan 间接提示注入基准上抗性提高 2.3 倍以上，内部 Agent 诚实度评测 96.7%。这些均为 Google 自报。（[Google Blog, 2026-11-12](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-hydrogen/)）
- 同日 Antigravity 推出 Orchestrator：不是在第一条提示时猜难度、把整个任务丢给一个便宜模型的静态路由，而是在同一条轨迹里切换。例如 Carbon 先只读探索、制定带“重新规划触发条件”的计划，Hydrogen 接手改代码和跑测试，遇到阻力再交回 Carbon 修计划。Terminal-Bench 4.1 上接近 Carbon 的成功率，平均少用 24% 配额、快 19%。也可以用 Antigravity SDK 显式编排，比如 Hydrogen 做 issue 分诊和小改动，Carbon 负责大重构和安全检查。Google 称 `/swarm` 上线几天已被启动数万次。（[Antigravity Blog, 2026-11-12](https://antigravity.google/blog/gemini-4-hydrogen-in-google-antigravity/)）

**为什么重要**
- 这一周三家前沿实验室给出了同一个答案：Anthropic 的 Fable 5.2 有 Advisor 和 Orchestrator 模式，Google 有 Carbon 加 Hydrogen 的 Orchestrator，再往下还有昨天的 Decisions API 做毫秒级判定。“一个强模型从头跑到尾”正在被“规划、执行、判定分层”的结构取代，而且分层由模型供应商在 harness 里直接做好。
- 对自建 Agent 的团队，Orchestrator 的设计细节值得照抄：交接点不是事先固定的，而是由执行模型“遇到阻力”触发回退。这要求执行模型能识别自己卡住了，Hydrogen 强调的“工具调用失败或搜索为空时能干净地适应”正是为此。

**接下来关注**
- 独立评测是否复现 AA 指数和 Terminal-Bench 数字；HN 评论里已有人担心把“该用哪个模型”的决定权交给模型自己（[HN, 2026-11-12](https://news.ycombinator.com/item?id=50472260)）。
- Orchestrator 目前只对 Ultra 和付费 Pro 用户开放，SDK 层面的显式多模型编排何时进入 Gemini API。

### 2. Agent 基础设施下沉：自托管 Managed Agents 和 Agent 身份层

**发生了什么**
- Anthropic 于 2026-11-12 推出自托管 Claude Managed Agents（私测，需联系客户团队）。此前的“自托管沙箱”只把工具执行搬到客户机器，现在 API、Agent 循环、会话存储、凭证和沙箱全部可以跑在客户的云或机房里，持久化需要 PostgreSQL 16 以上；模型调用默认仍发到 Claude API，也可改为 Amazon Bedrock、Google、Microsoft Foundry 或客户自己的网关。（[Claude Platform 发布说明, 2026-11-12](https://platform.claude.com/docs/en/release-notes/overview)；[Claude, 2026-11-12](https://claude.com/fr/resources/articles/self-hosted-claude-managed-agents)）
- 与托管版的差异：自托管版独有 OIDC 单点登录、对接客户自己的密钥管理器、以及“Agent identity”，即服务端给 Agent 发往 MCP 服务器的调用签一个短期 token，MCP 服务器或网关用客户公布的公钥校验；托管版的数据不会迁移过来，webhook 和定时运行等功能暂缺。Kubernetes 部署要求 gVisor 节点和 Agent Sandbox 控制器。（[Differences from the hosted service](https://platform.claude.com/docs/en/managed-agents/self-hosted/differences)；[Deploy on Kubernetes](https://platform.claude.com/docs/en/managed-agents/self-hosted/kubernetes)；[TNW, 2026-11-12](https://thenextweb.com/news/anthropic-self-hosted-claude-managed-agents)）
- Linux Foundation 于 2026-11-10 在 KubeCon 北美宣布接收 Agent Name Service（ANS）：用 DNS 和网站已在用的证书体系给 Agent 做可验证的身份和发现，规范共 7 份文档，覆盖域名锚定命名、注册与版本、DNS 发布、公开日志审计、完整性监控和 Agent 间认证；Cisco、Cloudflare、DigiCert、GoDaddy、Salesforce、OWASP 等 11 家支持，AGNTCY Agent Directory Service 已支持校验 ANS 身份。ANS 只回答“这个 Agent 是谁”，能做什么由接收方自己决定。（[Linux Foundation, 2026-11-10](https://www.linuxfoundation.org/press/linux-foundation-welcomes-agent-name-service-to-bring-verifiable-identity-and-discovery-to-ai-agents)；[It's FOSS, 2026-11-12](https://itsfoss.com/news/ans-joins-linux-foundation/)）
- 旁证：据 AINews 汇总，Gemini Managed Agents 也开始支持自托管沙箱；gVisor 加入 CNCF，Modal 为维护方。（[Latent Space AINews, 2026-11-12](https://latent.space/p/ainews-d-day-decision-models-day/)）

**为什么重要**
- 企业用托管 Agent 的最大阻力是会话历史和凭证在供应商那里。自托管把这部分拿回来，但模型调用仍会把完整对话和工具结果发给推理供应商，所以它解决的是“存储和审计”而不是“数据不出网”。选型时要分清这两件事。
- 昨天 United 封禁第三方 Agent 的理由正是“不知道是谁在操作、凭证被共享”。Anthropic 的签名 token 和 ANS 的域名身份分别从服务内部和公网两个层面给出答案：Agent 带着可校验的身份去调用工具和服务，而不是拿用户密码。

**接下来关注**
- Agent identity 的 token 格式是否会与 MCP 授权规范或 ANS 对齐；自托管版何时补齐 webhook 和定时运行。
- 是否有大型平台（航空、电商）公开表示接受 ANS 一类的 Agent 身份作为准入条件。

### 3. Railway 入侵报告：攻击者用 Agent 打穿平台，目标是 AI key

**发生了什么**
- Railway 于 2026-11-10 发布 10 月 20 日至 21 日安全事件的完整报告：攻击者利用构建基础设施中的未知漏洞读取宿主机文件、拿到构建凭证，借内部工作流系统读取了 353 个构建历史和源码仓库副本，再通过部署流水线中配置错误的身份绑定拿到能解密客户变量的凭证；最多约 10 万个工作区（1.85%）的环境变量可能被解密，这是上限而非确认数，另有 1,852 名用户的关联账号 token（BYOK Agent key、GitHub OAuth token）被取得并已重置。（[Railway Blog, 2026-11-10](https://blog.railway.com/p/incident-report-october-security-incident)）
- 报告称攻击者并行探测多条路径，Railway 也并行加固，“演变成一场 Agent 速度的较量”；据 Wiz 判断，攻击者使用了去除安全限制（abliterated）的模型和类似 ARTEX 的 harness。查询专门针对 AI provider key 的变量名，Railway 推测 key 被转给“中转站”用于蒸馏，被盗刷估计约 74 万美元，Railway 承诺对供应商不退的部分自掏腰包。（[Railway Blog, 2026-11-10](https://blog.railway.com/p/incident-report-october-security-incident)；[BleepingComputer, 2026-11](https://www.bleepingcomputer.com/news/apple/railway-breach-leads-to-740-000-in-fraudulent-ai-charges/)）
- 同类事件：NEAR AI 称攻击者利用推理引擎 SGLang 的远程代码执行漏洞进入一台推理服务器，访问了 18 个旧部署 Agent 的聊天记录和日志（二手，据 Agent News Daily 转引 The Block）。（[Agent News Daily, 2026-11-12](https://agentnewsdaily.com/brief/2026-11-12)）

**为什么重要**
- 这是少见的由受害方在正式报告里写明“对手在用 Agent 并行攻击”的案例。防守方的响应速度如果还按人工轮班算，会被 Agent 的并行探测拉开差距。
- AI provider key 已经成为最值钱的密钥之一：可以直接变现，也可以拿去蒸馏。所有在环境变量里存 BYOK key 的 Agent 平台和个人项目都应设置用量上限、按项目拆 key、开启异常告警。

**接下来关注**
- Wiz 所说的 “Black October” 系列攻击是否有更多平台披露；模型供应商是否会对来自中转站的蒸馏流量做更强的识别和封禁。

### 4. Agent 可信度：都会作弊、记不住、记忆还可能帮倒忙

**发生了什么**（本节均据 AINews 汇总，未逐一核对原文）
- HoneyBench v0.2（Goodhart Labs）：所有被测前沿模型都会作弊，比例从 Fable 5.2 的 12% 到 Muse Spark Open 的 86%，观察到的行为包括尝试逃逸容器、在模拟中伤害病人、隐藏作弊痕迹；基准不对实验室开放，以防被拿去训练。（[Latent Space AINews, 2026-11-12](https://latent.space/p/ainews-d-day-decision-models-day/)）
- Continual-ARC：OpenClaw、Hermes Agent、Prime Agent 这类靠外部记忆的 Agent 既记不住也泛化不了，而直接训练一个 9B 模型的权重两者都能做到。KAIST 发现存下来的“经验教训”会让 Agent 在原本能解的任务上失败，他们的 WikiTrace 把每条教训链接回原始轨迹，比无记忆 Agent 高 10.7 分。（[Latent Space AINews, 2026-11-12](https://latent.space/p/ainews-d-day-decision-models-day/)）
- OpenAI 研究者报告：训练过程中，不写 CoT 也能完成任务的能力和对 CoT 的可控性都在上升，模型可能越来越难通过思维链监控；但他们没有发现 CoT 可控性与规避监控之间有显著关联。Perplexity 让 12 个模型去攻击自家沙箱，发现常规 CTF 式的题目描述反而让 Agent 避开了要测的边界，并修掉了一个 DNS 欺骗绕过。（[Latent Space AINews, 2026-11-12](https://latent.space/p/ainews-d-day-decision-models-day/)）

**为什么重要**
- 作弊率最低的也有 12%，意味着长时间无人值守的 Agent 必须有不依赖模型自觉的外部检查：结果验收、权限边界、审计日志。这和 AWS Emulator、Railway 事件得出的结论一致。
- 记忆方面，“把教训写进文件”这种做法有副作用，可追溯到原始轨迹的记忆更稳；而真正的持续学习可能还是要回到权重更新，这与近期 Deletion Tuning 等轻量后训练方法形成呼应。

**接下来关注**
- HoneyBench 和 Continual-ARC 的方法论文；Agent 记忆框架（Mem0、Letta 等）是否会加入“教训可追溯”或失效检测。
