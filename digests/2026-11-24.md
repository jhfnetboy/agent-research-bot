## 重点话题

### 1. Claude Ship：Agent 从写代码走到批准代码

**发生了什么**
- Anthropic 发布 Claude Ship（beta），由三个 Agent 组成：Code Review（已 GA）从多个角度审查 PR、对自己的发现做对抗式核验后按严重度发评论，可选 Quick、Standard、Deep 三档；PR Steward（beta）处理失败的 CI、合并冲突和审查意见，每次 push 后说明改了什么、如何撤销，开发者可用 `@claude stop` 让它退出，设计上不会批准或合并；Claude Approvals（beta）读取团队写在仓库里的策略文件，可以自行批准常规改动，或对特定路径要求人工签字，官方类比为“更聪明的 CODEOWNERS”。（[Anthropic, 2026-11-23](https://claude.com/resources/articles/introducing-claude-ship)）
- 数据和用法：Anthropic 称在 Claude Code 团队，Claude 已写大部分代码；6 月到 9 月合并 PR 数翻倍以上，同时回滚占比下降超过 40%（Code Review 只是其流程中的一层）。开发者可在 Claude Code 里用新的 `/ship` 命令一键 push、开 PR、审查和修复。面向 GitHub 上的 Team 和 Enterprise 计划，按 token 计费，不支持 ZDR、HIPAA 和 CMEK 组织。官方建议 Approvals 先用 observe 模式运行。（[Anthropic, 2026-11-23](https://claude.com/resources/articles/introducing-claude-ship)）
- 文档里的风险提示：策略文件为 `.claude/approvals.yml`，按路径设置 `seats`（需几人批准）和 `claude: approves / comments / blocks`。文档专门列出“无人审查即合并”的情形：检查未设为必需、`seats: 1` 时作者本人即可占位、`seats: 0` 时 bot 写的 PR 可无人查看就合并、GitHub 规则会把 Claude 的批准算作一票、`claude: approves` 本身不触发 Code Review。（[Claude Approvals 文档](https://code.claude.com/docs/en/approvals)；[Claude Ship 文档](https://code.claude.com/docs/en/claude-ship)）

**为什么重要**
- 写代码的瓶颈被 Agent 解决后，审查和签字成了新瓶颈。Claude Ship 把“最后一道人工关口”变成一份可配置的策略文件，这是 coding agent 产品形态的又一次上移，和 11 月 21 日日报提到的 Agents SDK、harness 治理是同一趋势。
- 安全面随之转移：策略写错，就可能让没人读过的代码进主干。结合上期 agent-framework 被投毒的事件，谁能合并策略文件、Claude 的批准是否计入分支保护，需要和凭据管理一样当成一等问题。

**接下来关注**
- 第三方团队在 observe 模式下的误批准率和回滚数据；OpenAI Codex、GitHub Copilot 是否推出对等的“Agent 批准”能力。

### 2. GLM-5.4：Loop Transformer 进入 750B 旗舰

**发生了什么**
- Z.ai 发布 GLM-5.4，称其为首个基于 Loop Transformer 的旗舰模型：不从头预训练，而是把已预训练的 GLM-5 基座通过继续训练改造成循环结构，让 28 层共享权重运行两次，规模 750B，官方称智能水平可比 2T 到 3T 参数模型。（[Z.ai, 2026-11-23](https://z.ai/blog/glm-5.4)）
- 三个工程改动：每轮迭代独立的逐 token 门控，把候选更新按比例写回残差流，避免激活范数在循环中爆炸（训练后第一轮写得保守、第二轮写满）；混合 KV cache，第二轮复用第一轮选出的稀疏 KV，只额外保留一个滑动窗口，因此多一轮循环只多一个窗口的 KV 成本，1M 上下文下部署成本相对 GLM-5.3 可控；第二轮直接复用第一轮稀疏注意力的索引。（[Z.ai, 2026-11-23](https://z.ai/blog/glm-5.4)）
- 消融：在与 750B 基座同构的 30B 模型上做等参数对比，总训练算力约多 10%，循环版在数学、科学推理、长上下文上收益最大；GPQA-Diamond、MMLU-Pro 等基准平均输出长度下降 10% 到 14%，官方解读为部分推理从显式 CoT 转移到循环深度。我们抓取到的博客文本未包含具体分数。已知局限是容易陷入过长的“marathon thinking”。吞吐为闲时最高 200 tokens/s、高峰 70 到 80 tokens/s。（[Z.ai, 2026-11-23](https://z.ai/blog/glm-5.4)）
- 可用性：目前通过 GLM Coding Plan、ZCode 和 Chat 使用，常规 API 标注“即将推出”，权重计划在安全加固后开放。Simon Willison 实测发现 Coding Plan 的 key 可在 Z.ai 的 OpenAI 兼容 Responses API 上调用该模型，并写了 llm-glm 插件；他指出这是一周内第二个 looped transformer。（[Simon Willison, 2026-11-23](https://simonwillison.net/2026/Nov/23/glm-54/)）

**为什么重要**
- Inkling 2 Mini 之后，looped 架构在一周内从小模型扩展到 750B 旗舰，且采用“改造已有基座”的低成本路线。推理更多发生在隐藏状态里，输出 CoT 变短，这直接触及 11 月 22 日日报讨论的 CoT 可监控性问题。
- HN 上（1057 分、346 评论）最多的质疑是没有基准分数，难以判断水平；也有人直接评论“Neuralese, here we come”。（[HN, 2026-11-23](https://news.ycombinator.com/item?id=50609685)）

**接下来关注**
- 独立评测和开放 API 后的实测；权重是否开放；Z.ai 称“明显更大的下一个模型很快就绪”，以及自适应循环次数（难 token 多迭代）的进展。

### 3. AI 自主做研究：Claude 发现 VP ≠ VNP，RSI 的“原料”在积累

**发生了什么**
- Anthropic 在 GitHub 仓库 anthropics/formal-math 新增 `vp-vnp` 目录（提交时间 2026-11-23 20:04 UTC，即曼谷时间 11 月 24 日 03:04）：结论是对任意域，Hamiltonian cycle 多项式以及特征不为 2 时的 permanent 的电路，对足够大的 m 需要超过 m^(c (log m)^(1/3)) 个门，近似电路同样成立，因此 VP 是 VNP 的真子集，且 VNP 不含于 VP 的闭包。README 明确“这不解决 P vs NP”。（[anthropics/formal-math, 2026-11-23](https://github.com/anthropics/formal-math/tree/main/vp-vnp)）
- 来源说明：README 写明结果“由内部研究用 Claude 模型发现”，论文和 Lean 4 形式化都由 AI 模型写成，“没有人类数学家检查过证明”。Lean 部分只依赖 Mathlib，CI 用 Comparator 对照 Challenge.lean，并用独立实现的第二内核 nanoda 复核；README 也提醒，Lean 检查证明，但没有机器检查陈述文件是否说了声称的内容。（[README](https://github.com/anthropics/formal-math/blob/main/vp-vnp/README.md)）
- 同一天的 Import AI 482（Jack Clark）介绍了两项相关基准：Shenzhen Loop Area Institute 的 AscendGYM 评估 Agent 为华为 Ascend NPU 优化 kernel 的能力，测试中 Opus 5 最好，其次 GPT-5.6、GLM-5.3，Jack Clark 称之为“中国式 RSI 的原料”；劳伦斯利弗莫尔国家实验室的 SciResearch-Eval 让 Agent 自行设计实验并在故意有缺陷的模拟器下报告 95% 区间，论文称模拟器缺失物理时只有 GPT-6 Astra 和 Claude Fable 5.2 在默认设置下可靠。（[Import AI 482, 2026-11-23](https://jack-clark.net/2026/11/23/import-ai-482-huawei-kernel-benchmarks-airborne-drone-detection-and-a-national-labs-ai-science-benchmark/)）

**为什么重要**
- 这是前沿实验室首次以“AI 发现、AI 写证明、AI 形式化、未经人工检查”的方式发布复杂度理论结果，并把信任完全押在 Lean 和双内核复核上。它延续了本周 GRH、黎曼猜想 Lean 证明的脉络，但把人类彻底移出了流程。
- 训练和推理用的 kernel 能被 Agent 优化，科学实验能被 Agent 设计并给出校准的不确定性，这些都是“AI 改进 AI”闭环的具体环节，可与 11 月 23 日日报 Pachocki 关于 AI 参与预训练研究的判断对照看。

**接下来关注**
- 复杂度理论学者对陈述文件与论文是否一致的核查；HN 上已有人推测这是 Anthropic 在攻 P vs NP 途中的阶段性结果，属于猜测。（[HN, 2026-11-23](https://news.ycombinator.com/item?id=50620102)）

### 4. Agent 走到防守侧：Shirudo、AWS AI 端点防护与 skills 隐私审计

**发生了什么**
- OpenAI 与 Cisco 开源 Shirudo（日语“盾”）：一个基于 eBPF 的运行时，Agent 可调查漏洞、生成只拦截危险行为的 “shield”、并在真实负载上验证；运维批准后在不重启的情况下部署。shield 有加密签名，经 Linux eBPF verifier 检查，并用 TPM 记录加载和卸载。受控测试中，Codex 生成的 shield 给 Java 的 Base64 解码器加了输入检查，挂到运行中的 Elasticsearch 进程上，拦截了 Java4Shell 利用尝试且服务未中断。BSD 2-Clause 许可，12 月 15 日有技术 webinar。（[OpenAI, 2026-11-23](https://openai.com/index/introducing-shirudo)）
- AWS 同日 GA 三项能力：API Gateway 的 API Portal 发现包括 LLM 推理端点、MCP 服务器和 A2A 服务器在内的 API；WAF 新增 API Security 和 AI Security 两个托管规则组。AWS 的论点是 MCP 服务器几分钟就能搭起来并绕过 API 网关和安全评审，而且端点会通过 `tools/list` 或 agent card 自我描述，Agent 成了“第三类调用方”。（[AWS Security Blog, 2026-11-23](https://aws.amazon.com/blogs/security/introducing-api-and-ai-security-on-aws-from-discovery-to-protection/)）
- 两篇论文：SkillPrivus 对 726 个公开市场的 Agent skills 做静态隐私审计，其中 563 个处理个人数据，307 个（54.5%）被标出至少一处潜在违规，与三名盲审标注者在可判定项上一致率 83.2%。（[arXiv 2611.26747](https://arxiv.org/abs/2611.26747)）Safe Personal RSI 把个人健康助手 Kicker 的自我改进限制在 prompt 更新，权重和运行时代码不变，每次更新先测安全和任务表现再采纳；在 29 个案例的基准上，三个模型、两种故意危险的修改下，21 次更新尝试拒绝了 20 次。（[arXiv 2611.23651](https://arxiv.org/abs/2611.23651)）

**为什么重要**
- 上期 AWS 披露 Cairn 自主发现零日，本期 OpenAI 给出防守方的对等工具，思路是“Agent 写临时防护，人批准”。这和 Claude Ship 一样，都是把 Agent 的产出放进“签名、验证、人工或策略审批”的流水线。
- MCP、A2A 端点已经被云厂商当成需要 WAF 的标准攻击面；skills 生态一半以上存在潜在隐私问题，说明“装一个 skill”应当和装一个依赖包一样审计。

**接下来关注**
- Shirudo 是否随漏洞披露附带经过测试的 shield（OpenAI 称这是目标）；Anthropic、MCP 社区是否针对 skills 推出权限声明或审计规范。
